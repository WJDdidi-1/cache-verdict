# Validation: the generated GitHub Actions recipe runs

This verifies the CI recipe documented in [the README](../../README.md#ci-gating):
`init --github-action` writes `.github/workflows/cache-verdict.yml`, and the
ledger path and command sequence in that file produce a warm sample and a
verdict locally. The end-to-end test in
[`test/init.test.mjs`](../../test/init.test.mjs) also writes the workflow from a
fixture, asserts each required step and cache key, and executes the same
sequence under `npm test`.

The reproduction is scripted in
[`github-action-recipe.sh`](github-action-recipe.sh). It uses only the Node.js
standard library and this checkout's CLI, writes everything to a temporary
directory, and removes that directory on exit.

## Artifact under test

- Source: this checkout at `ddec24c` (the commit that added
  `init --github-action`) plus the milestone test and validation script,
  version `0.3.0`.
- CLI: `bin/cache-verdict.mjs` from that checkout.
- Fixture: a tiny npm project with `src/input.txt`, a `package.json` build
  script, and a build that spends 250 ms computing an artifact under
  `node_modules/.cache` and reuses it on a warm run.

The generated file pins `cache-verdict@0.3.0` for `run` and `check`; those
commands are present in the published 0.3.0 tarball, even though the
`--github-action` flag itself is new in this checkout. The local commands below
use the checkout CLI rather than `npx`, so the validation does not depend on a
release containing the flag.

## Output

`init --github-action` writes both files. The workflow restores the ledger and
stored cache with `actions/cache`, installs the npm project dependencies, then
runs the gate:

```console
$ node bin/cache-verdict.mjs init --github-action

Wrote .cache-verdict.json.
Wrote .github/workflows/cache-verdict.yml.
Review the install step, then commit the config and workflow so CI restores the same ledger.
note: npm's download cache defaults to ~/.npm; set npm_config_cache=.npm in CI to keep it project-local and measurable.
Review "command", "inputs", and "cachePath" before sampling.
```

The generated workflow in full:

```yaml
# Generated by `cache-verdict init --github-action`.
# Review the install and build steps, then commit this file with
# .cache-verdict.json. The ledger lives at .ci/cache-verdict/ledger.jsonl so it
# survives between builds; the local default is .cache-verdict/ledger.jsonl.
name: cache-verdict gate

on:
  push:
  pull_request:

permissions:
  contents: read

jobs:
  cache-verdict:
    runs-on: ubuntu-latest
    env:
      CACHE_VERDICT_LEDGER: .ci/cache-verdict/ledger.jsonl
    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-node@v4
        with:
          node-version: 22

      - name: Install project dependencies
        run: npm install

      - name: Restore the cache-verdict ledger and stored cache
        uses: actions/cache@v4
        with:
          path: |
            .ci/cache-verdict/ledger.jsonl
            .cache-verdict/store
          key: cache-verdict-${{ github.ref_name }}-${{ github.run_id }}-${{ github.run_attempt }}
          restore-keys: |
            cache-verdict-${{ github.ref_name }}-

      - name: cache-verdict run
        run: npx --yes cache-verdict@0.3.0 run

      - name: cache-verdict check
        run: |
          set +e
          npx --yes cache-verdict@0.3.0 check
          status=$?
          set -e
          if [ "$status" -eq 3 ]; then
            echo "::notice::cache-verdict needs another build before it can decide"
            exit 0
          fi
          exit "$status"
```

pays.

## What this proves

- `init --github-action` writes both the reviewable config and
  `.github/workflows/cache-verdict.yml`, and regenerating is reviewable: the
  existing config is kept.
- The generated workflow contains every step the gate depends on: checkout,
  Node setup, package-manager install, `actions/cache` for both the ledger and
  `.cache-verdict/store`, `cache-verdict run`, and `cache-verdict check` with
  exit 3 handled as "keep collecting".
- The cache key changes per run while `restore-keys` is scoped to the branch,
  so a later run can restore the newest matching entry even though
  `actions/cache` entries are immutable.
- The `CACHE_VERDICT_LEDGER` in the generated file is the ledger that `run`
  writes and `check` reads. It replaces the local default, so the samples live
  where the cache action can persist them.
- The command sequence in the README's hard-gate alternative
  (`init`, `run`, `run`, `check`) works on a project the repository has not
  seen, without hand-written YAML.

## What this does not cover

- It does not call the GitHub Actions cache service. It proves the paths,
  commands, and exit handling in the generated file; GitHub's restore/save
  behavior is the action's responsibility. The separate
  [shared-ledger validation](ci-ledger-checkout.md) simulates two fresh
  checkouts sharing a ledger and store.
- It runs two builds in one project. The generated workflow usually runs one
  build per job and relies on `actions/cache` to carry the ledger and store
  forward; the first job therefore records one cold sample and exits 0 through
  the exit-3 branch.
- It uses one small npm project. The install-step variants for pnpm, Yarn, Bun,
  Python, and Go are covered by `npm test`, not by this record.
- The generated file pins `cache-verdict@0.3.0`; the `--github-action` flag that
  writes it is not in the published 0.3.0 tarball. Publishing this change makes
  `npx cache-verdict@0.4.0 init --github-action` the one-command path.
