# cache-verdict v0.1.0

First release of `cache-verdict`, a CLI that times build-cache cold and warm
runs and says whether the cache pays for itself.

- Package: `cache-verdict@0.1.0`
- Tag: `v0.1.0`
- Requires: Node.js 18 or newer

## Why this release exists

A cache hit counter says that an entry was found. It does not say that the
build got faster. A warm build restored from another pipeline's cache can be
slower than a cold build, and a cache that churns keys or restores nothing can
look healthy while costing time. Version 0.1.0 measures the end-to-end build
for a declared cache key and turns the samples into one actionable verdict.

## What is in 0.1.0

- `cache-verdict init` detects Cargo, Gradle, Next.js, npm (including pnpm,
  Yarn, and Bun lockfiles), Python, or Go and writes a reviewable
  `.cache-verdict.json`. Use `--ecosystem`, `--command`, `--force`, or
  `--dry-run` to override or preview the result.
- `cache-verdict run` content-addresses the declared inputs, the command, and
  the cache paths; moves the declared cache paths aside; restores the stored
  cache for that exact key when one exists; times the build from a known state;
  stores the produced artifacts; and appends one sample to
  `.cache-verdict/ledger.jsonl`.
- `cache-verdict report` prints hit rate, median cold and warm totals, restore
  cost, net milliseconds per hit, cache size, and one verdict: `cache-pays`,
  `cache-costs`, `cache-churns`, `cache-never-hits`, or `cache-unobserved`.
  `--json` prints the same analysis as JSON.
- `cache-verdict check` exits 0 for `cache-pays`, 2 for a losing, churning,
  never-hitting, or unobserved cache, and 3 when more samples are needed, so a
  pipeline can gate on the measurement.
- `cache-verdict prune --keep N` evicts least-recently-used stored keys.
  `run --cold` adds a fresh baseline without removing the stored cache that the
  next normal run should hit.

## Install

```sh
npm install -g cache-verdict@0.1.0
cache-verdict --version
```

Requires Node.js 18 or newer. The package has no runtime dependencies.

From a checkout, before the registry serves this version:

```sh
npm install -g .
cache-verdict --version
```

## First measurement

```sh
cache-verdict init
cat .cache-verdict.json    # review command, inputs, and cachePath
cache-verdict run          # cold miss, then store
cache-verdict run          # warm hit, then report
cache-verdict report
```

The repository includes a runnable npm example:

```sh
npm run example
```

It copies [`examples/npm-build-cache/`](../../examples/npm-build-cache/) to a
temporary directory, runs `init`, two samples, and `report`, and removes the
copy afterwards.

## Measurement and safety properties

- The key is derived from file contents, the command, and the declared cache
  paths, not from file timestamps or a single lockfile.
- Declared cache paths are moved aside before a sample, so a cold sample starts
  from a known state. The pre-run contents are put back if the build fails.
- Everything the CLI writes stays under `.cache-verdict.json` and
  `.cache-verdict/` in the project. The CLI has no network code, so it does not
  upload samples or fetch a remote cache.
- The config is plain JSON and is reviewed before the first sample; `init`
  refuses to overwrite it without `--force`.

## Verification

The suite at this version contains 25 tests. CI runs it on Ubuntu, macOS, and
Windows with Node.js 18, 20, and 22, then packs the tarball, installs it into a
clean project, and runs the installed `cache-verdict` command.

The end-to-end tests cover:

- an identical key restoring on the second run and reporting `cache-pays`;
- a slower warm build reporting `cache-costs` with exit 2;
- changing inputs producing multiple keys and reporting `cache-churns`;
- a cache that is never restored reporting `cache-never-hits`;
- an empty `cachePath` reporting `cache-unobserved`;
- `run --cold` recording a baseline while the next normal run can still hit;
- `prune --keep` evicting least-recently-used keys;
- `run` refusing a cache path that would move the project itself;
- `report --json` and the initial "not enough samples" check behaving as
  documented.

## Scope

This is an early MVP. The commands and verdicts above are the scope; anything
not listed here is not implemented. The verdict is only as good as the declared
`command`, `inputs`, and `cachePath`, so review the config before trusting a
sample. Each project keeps its own local ledger; there is no cross-project
dashboard or hosted aggregation.
